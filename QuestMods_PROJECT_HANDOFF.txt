WRIST HUD (1.9.7, USER-REPORTED WORKING) → 1.9.8 CHANGES
--------------------------------------------
User request: "on my wrist it has my fps and safe or Not Safe ... check if people are around you and can see you ... if nobodys around you it says safe."

Implementation in Class1.cs (inside QuestMods.Mod):
- 1.9.8: the display has NO black plate/box any more. It is three TextMesh labels (FPS, status, info) rigidly parented to a controller transform, so it conforms to the wrist angle and sticks to the wrist (no billboard, no floating panel). Tablet buttons choose the wrist side (LEFT, falls back to RIGHT) and cycle a "Wrist Pose" preset (Back 60/45/75, Top 90, Palm 60, Flipped 60, Flat) that sets the local offset and tilt, so the text can be made to sit flush on the back of the wrist. Local scale is counter-scaled so the text keeps its size under any hand scale. In 1.9.7 the display was a billboarded quad.
- Line 1 shows FPS, sampled from Time.frameCount over 0.5s. Lines 2/3 show "SAFE" (green) / "NOT SAFE" (red) / "SCANNING" (yellow) and a short count such as "N:2 VIS:1" or "CLEAR 30m".
- 1.9.8: the local head is now read from PlayerController.Current.Head by reflection when Camera.main is unusable, matching the supplied ReturnToMainMenuAction reference. A watcher is added to LOOK only when the line of sight is clear AND the local head is inside their view cone (dot > 0.35 on their Head forward); if their Head transform cannot be read, a clear-LOS player is still counted, so behaviour stays fail-closed. The info line now shows N/VIS/LOOK counts.
- Safety scan runs 4x/second over Player.AllPlayers, skipping the local player by pointer and by PlayerController identity. One shared scan (TickSightGuard) feeds both the HUD and the new guards, so the guards still work when the wrist HUD toggle is OFF. A player counts as "nearby" within the configured range (default 30m; tablet button cycles 10/20/30/50/80m). "Can see you" means an UNBLOCKED line of sight between your head and theirs: Physics.Raycast is stepped past player bodies, held items, triggers and our own HUD props; solid world geometry (walls/terrain/props) means they cannot see you. No view-cone guess is made because remote head/gaze transforms are not verified on this IL2CPP build; a nearby player with clear LOS is conservatively NOT SAFE even if facing away.
- 1.9.8 guard semantics: "seen" = at least one seer (clear LOS + looking). "Fully away" = nearby 0, watchers 0 and unknown 0, held for 5 seconds. Disconnect on Sight calls GameModeManager.StopCurrentModeAsync("return to menu", true) by reflection, exactly as the supplied ReturnToMainMenuAction does, with a 12s cooldown. Turn Off on Sight force-disables every gameplay toggle (Grabby Hands, Super Speed, Fly, Air Grab, Any Connect, Auto Revive, Noclip, Show Durability, No Social, Dev Light, Make Pearl, Player ESP) and restores the previous values once fully away; the lock is re-applied every frame, so re-enabling something from the tablet while someone is watching does not stick. TP Away on Sight teleports to the saved waypoint furthest from the seer, or 60m directly away from them if no waypoints are saved.
- Note on the supplied ClientCommandHandler: that is SERVER-SIDE remote-console code (it accepts console commands and mod uploads from clients). It is not usable as a client "disconnect" and was deliberately NOT called; the ReturnToMainMenuAction path is used instead.
- Player ESP (1.9.8): one translucent capsule + head sphere + nameplate per remote player, drawn with Shader.Find("GUI/Text Shader") (ZTest Always, renderQueue 4000) so the silhouettes show through walls. All colliders on the ESP objects are destroyed, so ESP cannot affect grabs or the sight raycasts. ESP ignores the safe range and shows everyone; names come from Player.UserInfo.Username. It defaults OFF and is force-reset on launch.
- Fail-closed: if the player list cannot be read, the display says SCANNING; if a listed player's position cannot be read or the scan throws, it says NOT SAFE (count "?:N") rather than claiming SAFE.
- New tablet app page "INFO" (BuildSightHelpPage) explains each toggle in plain words. Tablet UI: "Wrist HUD (FPS/Safe)" toggle (defaults ON and is NOT force-reset on launch, unlike the gameplay toggles) and a "Safe Range: Nm" button. The radial wheel is untouched; Dev Tools 1/2 and the direct Grabby Hands toggle are preserved.
- Everything is read-only and client-side. It does not hide you from other players, change networking, or grant permissions.

Things to verify on-device for 1.9.8: that the parented (non-billboard) text sits at a readable angle for the chosen wrist/tilt, that GameModeManager.StopCurrentModeAsync exists with a matching signature, that TryCast<Player> + Player.UserInfo.Username work for ESP names, that "GUI/Text Shader" survives the Quest build, that teleport uses the existing TeleportLocalPlayer path safely, and that the 5s "fully away" hold feels right. COMPILE FIXES IN 1.9.10 (USER-REPORTED ERRORS)
---------------------------------------------
The user compiles this file in their own project. Their compiler reported, and 1.9.10 fixes:
- "The type or namespace name 'DayTimeManager' could not be found" -> MakeDay() no longer names the game type at compile time. 1.9.11 additionally fixed "Argument 1: cannot convert from System.Type to Il2CppSystem.Type": in this IL2CPP interop build Object.FindObjectOfType(Type) and FindObjectsOfType(Type) take Il2CppSystem.Type, so MakeDay walks Object.FindObjectsOfType<MonoBehaviour>() and matches mb.GetType().Name == "DayTimeManager" instead. It then sets field isUpdatingDaytime and calls UpdateRotation(0.25f, 0f) / UpdateAmbience() by reflection. General rule: never pass a System.Type to a Unity API in this file; use a generic overload with a compile-time type, or Il2CppInterop.Runtime.Il2CppType.From(t) / Il2CppType.Of<T>() when the parameter really is Il2CppSystem.Type.
- "The type or namespace name 'ParticleSystemRenderer' could not be found" -> the fog/mist scan now iterates Object.FindObjectsOfType<Renderer>() (UnityEngine.CoreModule) and still filters by GameObject name. Do not reintroduce ParticleSystemRenderer or ParticleSystem types; that module is not referenced in the user's project.
- "The name 'Il2CppType' does not exist in the current context" (twice) -> two pre-existing AddComponent(Il2CppType.From(...)) calls used the bare name. Always write the fully qualified Il2CppInterop.Runtime.Il2CppType.From(...), because the user's project has no using for that namespace.
- Warnings "field ... is assigned but its value is never used" / "is never used" for GrabbyHands.undockAttempts, seen, pickupLogs, insideUndock, earlyLogs -> those dead diagnostic counters were removed, along with every reset that touched them. If the user's compiler treats warnings as errors, do not add write-only fields.

Reference rules from this: use only types from assemblies the user already references (UnityEngine.CoreModule, the game assemblies, MelonLoader, Il2CppInterop.Runtime). Anything else - XR, particle systems, game manager types, TextMesh types - must be reached by reflection (Type.GetProperty/GetField, FindLoadedType).

GRAPHICS OVERHAUL ADDED IN 1.9.9 (UNTESTED ON QUEST)
----------------------------------------------------
User request: "add a graphic overhaul toggle with everything you can think of to make the game look amazing no fog no blue film etc."

One toggle, "Graphics Overhaul", on the Quest Mods tablet page, plus two buttons: "Overhaul View" (camera far plane 4000/6000/2500/1500m, default 4000 - the user asked for 4000 out of the box) and "Overhaul Sharp" (headset render scale 1.00/1.15/1.30/1.50x, default 1.15x). A second, separate toggle "Max Detail (LOD 0)" forces the highest-detail mesh on every LODGroup (default OFF because it is expensive).

What it changes while ON (everything is snapshotted first and restored when it turns OFF):
- Fog: RenderSettings.fog off, density 0, start/end 100000. This is what removes the milky blue distance haze.
- Ambient/blue tint: ambientIntensity 1.35, reflectionIntensity 1.15, and when ambient mode is Flat the ambient colour is reset to a neutral (0.62,0.64,0.68) instead of the cold blue; skybox _Exposure raised to 1.25 when the sky material has it.
- Quality: masterTextureLimit 0 (full-res textures), maximumLODLevel 0, lodBias 4 (distant props keep their high-detail mesh much further out), anisotropicFiltering ForceEnable, pixelLightCount 8, antiAliasing 4, shadowDistance 200, shadowCascades 4, shadowResolution VeryHigh, shadowProjection CloseFit, softParticles/softVegetation/realtimeReflectionProbes/billboardsFaceCameraPosition on, particleRaycastBudget 4096, skinWeights FourBones, streamingMipmapsActive off. Texture.SetGlobalAnisotropicFilteringLimits(9, 9) is also called so ground and road textures stay sharp at an angle. All of these go through reflection (QualitySettings property names) so a missing member on this Unity version cannot break the build.
- Cameras: every CameraType.Game camera gets allowHDR/allowMSAA on, farClipPlane raised to the Overhaul View value, useOcclusionCulling turned OFF (occlusion culling is what makes far geometry and whole chunks pop out of existence before you reach them), and SolidColor clear flags switched to Skybox. The near plane is deliberately NOT touched (a smaller near plane costs depth precision and causes z-fighting).
- Headset: XRSettings.eyeTextureResolutionScale set to the Overhaul Sharp value and renderViewportScale 1.0, both by reflection through FindLoadedType("XRSettings") so there is no XR assembly reference.
- Post-processing / colour grading / overlays: scene MonoBehaviours are matched by type name (exact list plus short distinctive fragments like "fog", "postprocess", "colorgrading", "tonemap", "vignette", "bloom", "ambientocclusion") and disabled; renderers in the camera hierarchy and particle renderers whose GameObject name contains fog/mist/haze/tint/vignette/overlay/underwater are hidden. Every disabled component is logged as "[Graphics] Disabled <Type> on '<object>'" and re-enabled on toggle off. Nothing named QuestMods_* is touched, and ambiguous words like plain "tint" are only used for renderer names, never for gameplay scripts (item tinting).
- Re-applied every 2 seconds while ON so the game's own scene scripts cannot switch fog/texture limits back on. Scene loads re-scan for new volumes and re-apply the core settings.

Safety: all of it is client-side visuals. Nothing is sent to other players. Turning the toggle OFF restores the snapshotted fog, ambient, camera, quality and XR values and re-enables every component/renderer it disabled. The toggle is also part of the "Turn Off on Sight" panic set, so a panic returns the original visuals too.

- Far-detail work (1.9.12, the "far away things look bad" complaint): ApplyTerrainBoost() finds the Terrain type by reflection, gets every terrain with FindObjectsOfType(Il2CppType.From(terrainType)) and, per terrain, snapshots then sets basemapDistance 100000, heightmapMaximumLOD 0, detailObjectDistance 450, treeDistance 4000, treeBillboardDistance 2000, treeMaximumFullLODCount 1200, drawTreesAndFoliage true. Unity normally switches distant terrain to a low-res basemap and a coarse heightmap LOD, which is exactly why far hills looked flat and blurry; raising both keeps the real terrain shader and full geometry far out. All original values are captured in TerrainSnap and written back on toggle off. Terrain and LODGroup are never named at compile time (only through FindLoadedType + Il2CppType.From) so no new assembly reference is needed.
- Max Detail (LOD 0) (1.9.12, reworked 1.9.13): defaults ON. TickMaxDetail() re-forces LODGroup.ForceLOD(0) every 2s for groups within 500m of the player only - forcing LOD0 on the whole world is pure frame-time burn for no visible gain. RestoreMaxDetail() walks the groups with ForceLOD(-1) when the toggle is turned off. Reflection only, as above.

FAR-DETAIL AND LIGHTING REWORK IN 1.9.13
----------------------------------------
User feedback on 1.9.12: "meh terrain looks shitty and also far objects just go all out and add actual like improvements to shadows lighting".
- Terrain: 1.9.12 set basemapDistance to 100000, which makes the terrain shader alias badly at long range and looked worse. 1.9.13 sets basemapDistance 6000, and adds the value that actually fixes faceted hills: heightmapPixelError 1.2 (Unity default is about 5). Also detailObjectDistance 600, detailObjectDensity 1, treeDistance 5000, treeBillboardDistance 2500, treeMaximumFullLODCount 2000, treeLODBiasMultiplier 2, heightmapMaximumLOD 0, drawTreesAndFoliage true, followed by Terrain.Flush() if the build has it. All ten members are snapshotted per terrain in a Dictionary<string, object> so RestoreTerrain() puts every one back.
- Shadows: shadowDistance 300, shadowCascades 4, shadowResolution VeryHigh, shadowProjection StableFit (the sun moves, so stable fit is right for a big world), shadowCascade4Split (0.05, 0.15, 0.4) so the near cascade is sharp instead of the four cascades being spread over the whole view, shadowNearPlaneOffset 1.
- Lights: ApplyLightBoost() finds every Light, keeps directional ones only, snapshots intensity/shadows/shadowStrength once, then sets LightShadows.Soft, shadowStrength 0.95 and intensity = original * 1.12. The multiplication is always from the stored original, never from the current value, because the sun intensity changes with time of day and a periodic re-apply would otherwise run away. RestoreLights() puts the originals back.
- Ambient: RenderSettings.ambientMode is set to Trilight with sky (0.58,0.62,0.72), equator (0.52,0.50,0.46) and ground (0.34,0.31,0.26), ambientIntensity 1.25, reflectionIntensity 1.3 and skybox _Exposure 1.3. The old flat cold ambient is what made everything look washed out. All of it is snapshotted and restored.
- Far objects: lodBias raised to 6, maximumLODLevel 0, streaming mipmaps off. Max Detail (LOD 0) is now ON by default, 500m radius.
- New toggle "Keep Post FX (bloom/contrast)": when ON, ScanAndDisableGraphicsExtras() skips everything in graphicsPostTypes / graphicsPostFragments (volume, colour grading, tonemapping, bloom, vignette, grain, SSAO, DoF, etc.) and still disables fog volumes, underwater and blue-film overlays. This exists because removing the game's grading can make terrain look flat; if the user reports a washed-out look, tell them to flip this on.


Known trade-offs / things to verify on-device: full-res textures + 200m shadows + a 4000m far plane + occlusion culling off cost GPU time (and the extra geometry is the single biggest cost), so watch the wrist FPS readout and lower "Overhaul Sharp" first, then "Overhaul View", if it drops, so watch the wrist FPS readout and lower "Overhaul Sharp" first if it drops; disabling the global post-process Volume removes bloom as well as the blue tint (ask for a sub-toggle if bloom should stay); "antiAliasing" is usually fixed at startup on Quest and may be ignored; if a wanted visual effect is disabled by the name scan, its "[Graphics] Disabled ..." log line names it.

2.0.0 FEATURES
--------------
- Arm display: the wrist HUD is now an ARM display. wristPoses holds eight presets (Forearm A/B, Forearm Hi/Lo, Forearm In/Out, Wrist Back, Flat). The forearm presets move the text up the controller transform (y 0.06-0.115, z -0.02 to -0.04) and roll it 90 degrees on Z so the lines run sideways along the forearm and sit flat against it. Default is "Forearm A". The tablet button is "Arm Display: <pose>". FPS and info lines are purple (0.78,0.45,1.0 and 0.58,0.32,0.92); only SAFE / NOT SAFE / SCANNING keep their green/red/yellow.
- Sky (part of Graphics Overhaul): 220 star quads plus 3 planet spheres on a HarmonyClient_Sky root, placed at 72% of the camera far plane inside a 600-3200m clamp, above the horizon, seeded by System.Random(4711) so the constellation is stable. The root follows the camera every frame (so the stars never get closer) and rotates 0.5 deg/s. Stars use Sprites/Default (double sided, ZWrite off) so they are occluded by terrain but visible in the sky; planets use Unlit/Color. All colliders destroyed, shadows off. Stars are hidden during the day and shown at night using GameTimeManager.IsNight read by reflection; if that flag cannot be read the stars stay visible.
- Night look: when IsNight is true the overhaul raises reflectionIntensity to 1.7, skybox exposure to 1.55 and uses a deep blue Trilight ambient instead of the daylight one.
- Make Day fix: DayTimeManager fields are private, so ApplyMakeDay() sets isUpdatingDaytime to false (property first, then field), calls UpdateRotation(0.25f, 0f) and UpdateAmbience(), and pushes GameTimeManager.IsNight to false. The override is held for 10 seconds by TickMakeDayLock() because the server re-syncs the fixed-daytime flag, which is why the old one-shot version appeared not to work. The draw-distance work no longer overwrites the game's ambient when a DayTimeManager exists (HasGameAtmosphere()), which was the other reason Make Day looked broken.
- P-Noclip: pref PlayerNoclip, "P-Noclip (through players)". It walks the local PlayerController's colliders against every other player's colliders and calls Physics.IgnoreCollision(a, b, true) in both directions of the pair, refreshed once a second so new players are covered. Terrain, buildings and props keep their collisions, and the existing layer-based Noclip toggle is untouched. Turning it off calls the same walk with false.
- Purple tablet: ApplyTabletTheme() scans the TabletUILib assembly (and live tablet MonoBehaviours) for any Color member whose name mentions color/colour/accent/theme/tint and sets it to (0.55,0.25,0.95). If TabletUILib exposes no such hook it logs that and leaves the tablet alone - there is no documented theme API, so this is best effort, not a guarantee.
- P-Noclip and the graphics/detail toggles are all part of the "Turn Off on Sight" panic set.

2.1.0 ADDITIONS
--------------
- Make Night: same reflection path as Make Day but with dayProgress 0.75 and GameTimeManager.IsNight pushed to true. ApplyMakeDay(type, target, progress, isNight) now takes the time as a parameter; makeDayProgress / makeDayIsNight are stored so the 10s hold re-applies the same time.
- P-Noclip modes: playerNoclipMode 0 = PLAYERS (the old per-collider Physics.IgnoreCollision behaviour), 1 = PROPS+PLAYERS (layer matrix, terrain layer excluded), 2 = EVERYTHING (layer matrix, terrain included - this is the default, per the user asking to noclip everything and not just terrain). SetLayerCollisionIgnores() records the previous value of every (playerLayer, otherLayer) pair with Physics.GetIgnoreLayerCollision before calling Physics.IgnoreLayerCollision and restores all of them when the toggle goes off or the mode changes. Player layers come from every Collider under PlayerController.Current. The layer matrix is global, so the restore list is also flushed on scene load.
- Performance Mode: the user reports lag that is the same with the graphics overhaul on or off, so this targets CPU work, not visuals. While ON: Physics.autoSyncTransforms false (avoids a transform sync before every physics query), Time.fixedDeltaTime raised to 0.0333 (30Hz physics instead of 50Hz), QualitySettings.vSyncCount 0, Application.targetFrameRate 72, and SkinnedMeshRenderer.updateWhenOffscreen false for every skinned mesh found (rescanned every 8s, all restored on OFF). It also slows our own scans: sight guard 4Hz -> 2.5Hz, ESP 5Hz -> 2Hz, Max Detail 2s -> 6s, sky billboards 0.4s -> 0.9s. Everything is snapshotted in ApplyPerfMode and put back when the toggle is turned off.
- Reminder: Time.fixedDeltaTime and the layer collision matrix are global engine state. Restoring them relies on the snapshot; if the game changes them afterwards, the snapshot is still what gets written back on toggle off.

AURA AND GRASS IN 2.2.0 (UNTESTED ON QUEST)
-------------------------------------------
The user supplied the game's ShellAnimator / StatEffectShellAnimator / ShellSetting sources and their TownGrass mod, asking for a constant purple shell with pink/white/blue particles and a recoloured ("cool") grass, both always on.

Aura (pref "Aura", default ON, NOT reset at launch):
- Why it is not built on ShellAnimator: that class lives in Alta.PlayerEffects, which this project does not reference (the DayTimeManager error proved the Alta atmosphere assembly is not referenced either). It is also a per-character system driven by stat effects, not something to bolt a permanent shell onto.
- Instead BuildAura() makes HarmonyClient_Aura with: a Sphere primitive scaled (1.5,1.7,1.5) at 1.05m as a translucent shell (Sprites/Default, alpha pulsing 0.10-0.16, renderQueue 3100, ZWrite off), 26 billboarded Quad "bits" in the palette pink (1,0.42,0.85), white, blue (0.45,0.65,1), purple (0.72,0.38,1) orbiting at radius 0.55-1.0m with per-bit phase/speed/bob and a size pulse, and a purple Point Light (range 5, intensity 1.2-1.55 pulsing, no shadows) so it actually lights the ground.
- TickAura() runs every frame: it moves the root to PlayerController.Current.PlayerFeetPosition, pulses shell alpha and light colour/intensity, and updates the bit transforms at 20Hz (0.05s). All colliders destroyed, shadows off.
- The palette is the same purple used by the arm display and the tablet theme, so the whole mod has one look.

Grass overhaul (pref "Grass Overhaul", default ON, NOT reset at launch):
- This is the user's TownGrass mod folded into Harmony Client, so they only run one DLL. It reads the same baked TGR4 grass data and rebuilds patches around the player: near 26m full detail, out to 70m with a 45% random blade subset, two patch builds per frame, only in a scene whose name contains "Overworld".
- Data source order: UserData/TownGrass/grass.bin, then UserData/HarmonyClient/grass.bin, then the embedded "grass.bin" resource of any loaded assembly (i.e. TownGrass.dll). If none is found it logs once and stays off - it never throws.
- DEFLATE is done through reflection on System.IO.Compression.DeflateStream(Stream, CompressionMode) so the project does not need a System.IO.Compression reference; the returned object is cast to System.IO.Stream and read normally.
- Mesh building uses real managed arrays (Vector3[] / Color[] / int[]) and relies on Il2CppInterop's implicit T[] -> Il2CppStructArray<T> conversion when assigning Mesh.vertices / Mesh.colors / Mesh.triangles. If that ever fails to compile, the fallback is the TownGrass reflection+Marshal approach.
- The "cool" recolour: vertex colours are lerped from a dark purple root (0.13,0.03,0.30) to a per-blade tip that mixes hot pink (1,0.42,0.88) and blue (0.42,0.66,1) by the blade's random byte, with a smoothstep height curve. Every mesh is doubled and the second copy has flipped winding, so blades are visible from both sides.
- Materials: Shader.Find("Township Tale/Grass"), then Cheap/LitVertColor, then WindFoliageVertexColor, then Sprites/Default (unlit neon) as a guaranteed fallback. The game grass shader gets _Color pink-white, _DarkeningFactor 0.35, _Randomness 0.35, _SwayStrength 0.16 and _LightInfluence 1.6; the far material copies the no-sway shader.
- BlendShader/towngrass.bundle is deliberately NOT used: the user is dropping it in UserData/TownGrass, but Shader.Find covers the built-in shaders, which is what the neon fallback is for.

LAG PASS IN 2.3.0
------------------
The user says the lag is present with the graphics overhaul ON or OFF, so the overhaul is not the cause; this pass attacks our own per-frame cost and the few things in the mod that draw a lot.

1. Frame-time profiler. PerfBegin()/PerfEnd(name) wrap every tick inside SyncTabletToggles (sight, hud, esp, graphics, lod0, makeday, perfmode, pnoclip, sky, aura, grass) plus the whole OnUpdate body ("all"). PerfFrameDone() logs one line every 10s: "[Perf] frame X ms | our ticks Y ms | name=ms ...". Ask the user for that line - it names the offender instead of guessing.
2. FindLoadedType had no negative cache: any type name that did not exist was re-scanned across every assembly on every single call. Misses are now cached as null, so it costs one scan for the lifetime of the process.
3. Max Detail (LOD 0) is now OFF by default and no longer storms reflection: the LODGroup list is cached and rescanned only every 30s, and ForceLOD is applied per group at most every 10s (20s in performance mode) instead of every 2s.
4. Sky: the 240 stars are ONE combined mesh (single draw call) with quads facing the centre of the sky, so no per-star billboarding runs any more. This replaced ~220 GameObjects/draw calls updated every 0.4s.
5. Aura: the orbiting bits are one dynamic 22-quad mesh, rebuilt at 20Hz, instead of 26 GameObjects with their own transforms. The purple point light is now opt-in ("Aura Light (costs frames)", default OFF) because an extra real-time light raises the cost of every lit object in the scene.
6. Occlusion culling: turning it off is what draws the far world and is very expensive. It is no longer part of the Graphics Overhaul; it is its own toggle "Render More (no occlusion)" (default OFF), so the overhaul keeps the game's occlusion culling unless asked otherwise. Toggling it re-applies the camera settings immediately.
7. Grass: 18m near / 45m far instead of 26/70, one patch build per frame instead of two, and in performance mode the far ring is cut to 1.5x the near radius.
8. Reflection caches: FindHeadTransform reflected over nine names on every call (several times per player per 4Hz scan); it now caches the member list per type and the resolved transform per controller for one second. Camera.main and GameTimeManager.IsNight are both cached for one second instead of being looked up per frame.
9. Performance Mode additionally raises Physics.sleepThreshold to 0.02 (saved and restored) and shortens the grass ring.

If the profiler shows "all" (the whole OnUpdate) far above the sum of the parts, the cost is in the older pre-Harmony systems bounced there (TabletProbe, DevWheelBridge, DebugStateMonitor, GrabbyHands), which are timed together as part of "all" and are the next thing to instrument.

HOW THE CURRENT SOURCE IS ORGANIZED
-----------------------------------
The namespace is QuestMods and the entry point is QuestMods.Mod : MelonMod. Most integration is reflection-based to accommodate Quest IL2CPP proxy types and the user's reference limitations.

1. Startup and developer flags
   - OnInitializeMelon patches QuickAccessMenuAction initialization and selected getters using Harmony, then sets up diagnostics and the developer-wheel bridge.
   - InitializeForPlayer prefixes force the local developer initialization flag true; IsDev, UserRoles.IsDeveloper, and IsIgnored getter patches also attempt to expose developer actions. These are client-side changes and cannot grant server-enforced authority. Broad IsIgnored overrides are experimental and may expose incompatible actions.
   - Harmony registration does not prove a native IL2CPP call will reach a patch. Runtime log evidence is necessary.
   - Avoid starting new risky NestingMenuAction.Run detours during application startup: previous experimental versions crashed, although the exact cause was not conclusively established.

2. Developer and Quest Mods wheels
   - DevWheelBridge waits until in-game, reflects over QuickAccessMenuController runtime objects, and targets owned controller extension clones, not prefab assets. It reads the normal and developer arrays, appends missing Dev Tools 1/2 to the root wheel, and prepares Quest Mods.
   - QuestModsMenu creates a native nested menu by cloning existing game action assets. It converts the local Player.Current proxy to Il2Cpp.Player when necessary using reflected interop TryCast/Cast; an IPlayer proxy cannot simply be passed to InitializeForPlayer.
   - The Fly/debug-movement child is cloned from the native ToggleDebugMovementMenuAction. It is initialized for the local player but not run or automatically enabled.
   - Grabby Hands is presented as a direct toggle. It uses a cloned nesting action and a deferred Harmony prefix on SpawnNestedBubbles; it suppresses nested spawning only for the verified custom clone and queues a toggle request for the update loop. If the hook is bypassed, fallback detection can mark Grabby Hands unavailable rather than pretending the toggle worked.
   - Two local wheel controllers and their actual Controller/Interactor IDs are registered. The mod uses exact identity and IsLocal checks rather than object-name or transform-distance guesses.

3. Debug movement and diagnostics
   - DebugStateMonitor reads local IsDebugMovement and logs changes. It does not enable it. The native action itself controls the movement toggle when selected.
   - TabletProbe and speed/developer diagnostics are integrated into the existing mod. Some are verbose, but they do not implement a separate tablet/board.
   - Do not reintroduce the earlier dual validity/active getter hook design. In 1.6.1 the validity probe hit the active hook and the button remained red/unselectable; native method sharing or patch interference was plausible but not proven.

4. Grabby Hands in 1.9.6
   - The toggle defaults OFF. SceneLoaded clears state and disables it. The wheel hook is deferred until in-game; grab/slot hooks are installed when first enabled, not at application startup.
   - StartInteract interception is diagnostic only in 1.9.4–1.9.6. It does not pre-undock.
   - BeforeCheckHold is an experimental Harmony prefix on Interactor.CheckHold(PlayerInput), the local grab input path identified in the user-supplied Mono source. The Quest log for 1.9.5 shows this hook fired.
   - Checks include enabled state, verified exact local interactor/controller identity, IsLocal, and not already interacting or toggle-holding. If verification fails, normal game behavior is allowed.
   - It calls the game's SelectBestFromCurrent. If that returns a target, normal grab proceeds; the fallback does not force a different one. This selector does perform game scoring and may update game state, so calling it before the original CheckHold is not purely read-only.
   - If there is no selected target, the fallback inspects colliders returned by GetColliderOverlap and maps them with ColliderExtension.GetComponentIncludingBody<Interactable>. An unambiguous candidate must resolve to a PickupDock, or in 1.9.6 a directly touched Pickup that is verified to be that dock's current DockedPickup. A dock and its own current pickup can count as one logical target. Unrelated overlaps or different slots are rejected rather than guessed.
   - If the game buffer returns 10 colliders, 1.9.6 attempts a reflected Physics.OverlapCapsule using the same trigger positions, collision mask, radius/scale, and default trigger policy from the supplied reference code. It refuses partial/oversized results or failure to resolve required runtime members. This full-overlap path is UNTESTED on Quest.
   - It verifies the slot is active, its contents and quantity are readable, the pickup reports IsDocked, the pickup points back to that slot, and player ownership matches when the slot is owned. It then invokes the native GetConfirmationOnInteractable on the identified target. The game's forwarding/interaction path is expected to undock if allowed.
   - The mod does not disable grab assist. With the toggle ON, its fallback may prioritize one nearby slot over a more distant grab-assist target if direct native selection found none.
   - After confirmation, 1.9.6 records whether the held object matches the original pickup, the slot, or another object, plus whether the original pickup remains docked and whether the slot now contains the original or a different pickup. These diagnostics are not proof of server persistence.
   - If confirmation throws after invocation starts, the prefix avoids immediately issuing a second native grab that might duplicate side effects. Otherwise failures fall back to ordinary game handling. Some reflection/member names and IL2CPP behavior remain unverified.

WHAT THE USER-SUPPLIED GAME SOURCE REVEALED
------------------------------------------
These are facts about the supplied Mono reference; check Quest compatibility before relying on exact implementation details.

Interactor:
- CheckHold(PlayerInput) is subscribed to Interact and HardInteract action start events. It calls OnStartInteractionAttempt, checks local/held state, then may use grab assist or SelectBest(GetColliderOverlap(), out target), and calls GetConfirmationOnInteractable.
- OnStartInteractionAttempt primarily updates the interaction timeout when timing-out is enabled. Its name alone did not establish a generally useful target callback, and the 1.9.2 run did not log it despite hook registration.
- SelectBestFromCurrent calls GetColliderOverlap and SelectBest. SelectBest builds OverlapInteractables from interactable colliders, applies IsInteractable/channels, and asks each target to AssessInteraction. It is not guaranteed to select a non-interactable or score-rejected shop item.
- The reference collider overlap uses Physics.OverlapCapsuleNonAlloc with an internal 10-element collider array, last physics trigger position, current trigger position, scaled radius and collision mask.
- GetConfirmationOnInteractable may perform forwarding and ownership/interaction checks before calling StartInteract or waiting for confirmation. StartInteract itself also performs CheckForward and CheckInteractAllowedAndReplace before Interact.
- StartInteract arguments are (Interactable, isFromNetwork, isForced, isForcingHold). Remote/network interactions must not be treated as local user grabs.

PickupDock:
- A PickupDock is itself an Interactable and may expose HasDockedPickup, DockedPickup, QuantityStored, IsOwnedByPlayer and PlayerController.
- Its CheckForward can return the docked pickup, but also contains ownership/quantity checks and mutates state including forwarding/clientDocked. Do not call it as if it were a harmless getter.
- AssessScore can reject a local grab if RawInput.HardGrab is false. Different slots/settings may behave differently.
- A docked Pickup can be marked IsInteractable=false; the slot may be the actual selectable target.

Pickup:
- Pickup extends Interactable. IsDocked is based on Dock != null.
- Pickup.Interact calls Undock(interactor, true, 1) when Dock is non-null, then performs dock-specific grab setup. Prematurely undocking can change forwarding and the isGrabbingFromDock state.
- The original mod request used the same Undock(interactor, true, 1) pattern. The current experiment leaves this call to the native interaction path rather than calling it before forwarding.
- ForwardTo is a collection in the supplied reference, not a single linked interactable. Do not use the 1.9.3 single-target diagnostic as a correct model.
