1.11.0 CHANGES
--------------
Super Speed (fixes "no stat manager"):
- Candidate owners are now gathered from the character, PlayerController.Current, the smooth-locomotion proxy and its Character/character/CharacterController members, Player.Current and each of its character/controller members, plus each owner's Health.
- A candidate counts as a stat manager if it can answer a GetStat-style call (GetStat, TryGetStat, GetStatValue, TryGetStatValue, Get(key)) whatever its member is called; every member whose name contains "stat" is scanned, and a Stat proxy's back-reference (Manager/Owner) is followed.

Grabby Hands (fixes "back hands or pockets"):

- When the expanded capsule still finds no usable slot, an unmasked Physics.OverlapSphere (2.5 m) around the hand is swept and every interactable in it is classified the same way. The "no overlap" case no longer aborts before that sweep.
- Still never undocks and never guesses between slots: the nearest slot is chosen and the game's own confirmation decides.

Grab by Name (new, fourth bubble, violet 0.85/0.05/1.00):
- Port of the PC mod's GrabByName/IsPickupTyped: find the local interactor(s) recorded by Grabby Hands, enumerate live pickups (Resources.FindObjectsOfTypeAll of the Pickup type, or a MonoBehaviour scan filtered by a base-type walk to a type named "Pickup"), keep those whose name contains the keyword (case-insensitive), then call the interactor's own StartInteract(pickup, false, false, false).
- Stops an existing interaction first; only undocks and retries once if the pickup is still docked after the plain grab (per the standing rule that the native grab goes first).
- Limited to 20 grabs per press, logs scanned/matched/grabbed counts, and is a one-shot action, not a toggle.

HOW THE CURRENT SOURCE IS ORGANIZED
-----------------------------------
The namespace is QuestMods and the entry point is QuestMods.Mod : MelonMod. Most integration is reflection-based to accommodate Quest IL2CPP proxy types and the user's reference limitations.

1. Startup and developer flags
   - OnInitializeMelon patches QuickAccessMenuAction initialization and selected getters using Harmony, then sets up diagnostics and the developer-wheel bridge.
   - InitializeForPlayer prefixes force the local developer initialization flag true; IsDev, UserRoles.IsDeveloper, and IsIgnored getter patches also attempt to expose developer actions. These are client-side changes and cannot grant server-enforced authority. Broad IsIgnored overrides are experimental and may expose incompatible actions.
   - Harmony registration does not prove a native IL2CPP call will reach a patch. Runtime log evidence is necessary.
   - Avoid starting new risky NestingMenuAction.Run detours during application startup: previous experimental versions crashed, although the exact cause was not conclusively established.

2. Developer and Quest Mods wheels
   - DevWheelBridge waits until in-game, reflects over QuickAccessMenuController runtime objects, and targets owned controller extension clones, not prefab assets. It reads the normal and developer arrays, appends missing Dev Tools 1/2 to the root wheel, and prepares Quest Mods.
   - QuestModsMenu creates a native nested menu by cloning existing game action assets. It converts the local Player.Current proxy to Il2Cpp.Player when necessary using reflected interop TryCast/Cast; an IPlayer proxy cannot simply be passed to InitializeForPlayer.
   - The Fly/debug-movement child is cloned from the native ToggleDebugMovementMenuAction. It is initialized for the local player but not run or automatically enabled.
   - Grabby Hands and Super Speed are presented as direct toggles. Both use cloned nesting actions and the same deferred Harmony prefix on SpawnNestedBubbles (WheelToggleRouter.BeforeSpawn dispatches to each); it suppresses nested spawning only for the verified custom clones and queues a toggle request for the update loop. If the hook is bypassed, fallback detection marks that toggle unavailable rather than pretending it worked.
   - BubbleTint only recolours the three Quest Mods bubbles (Fly red, Grabby Hands green, Super Speed blue) by duplicating the bubble's current shared material per action. It adds no Harmony patches and cannot change menu behaviour.
   - Two local wheel controllers and their actual Controller/Interactor IDs are registered. The mod uses exact identity and IsLocal checks rather than object-name or transform-distance guesses.

3. Debug movement and diagnostics
   - DebugStateMonitor reads local IsDebugMovement and logs changes. It does not enable it. The native action itself controls the movement toggle when selected.
   - TabletProbe and speed/developer diagnostics are integrated into the existing mod. Some are verbose, but they do not implement a separate tablet/board.
   - Do not reintroduce the earlier dual validity/active getter hook design. In 1.6.1 the validity probe hit the active hook and the button remained red/unselectable; native method sharing or patch interference was plausible but not proven.

4. Grabby Hands in 1.9.6
   - The toggle defaults OFF. SceneLoaded clears state and disables it. The wheel hook is deferred until in-game; grab/slot hooks are installed when first enabled, not at application startup.
   - StartInteract interception is diagnostic only in 1.9.4–1.9.6. It does not pre-undock.
   - BeforeCheckHold is an experimental Harmony prefix on Interactor.CheckHold(PlayerInput), the local grab input path identified in the user-supplied Mono source. The Quest log for 1.9.5 shows this hook fired.
   - Checks include enabled state, verified exact local interactor/controller identity, IsLocal, and not already interacting or toggle-holding. If verification fails, normal game behavior is allowed.
   - It calls the game's SelectBestFromCurrent. If that returns a target, normal grab proceeds; the fallback does not force a different one. This selector does perform game scoring and may update game state, so calling it before the original CheckHold is not purely read-only.
   - If there is no selected target, the fallback inspects colliders returned by GetColliderOverlap and maps them with ColliderExtension.GetComponentIncludingBody<Interactable>. An unambiguous candidate must resolve to a PickupDock, or in 1.9.6 a directly touched Pickup that is verified to be that dock's current DockedPickup. A dock and its own current pickup can count as one logical target. Unrelated overlaps or different slots are rejected rather than guessed.
   - If the game buffer returns 10 colliders, 1.9.6 attempts a reflected Physics.OverlapCapsule using the same trigger positions, collision mask, radius/scale, and default trigger policy from the supplied reference code. It refuses partial/oversized results or failure to resolve required runtime members. This full-overlap path is UNTESTED on Quest.
   - It verifies the slot is active, its contents and quantity are readable, the pickup reports IsDocked, the pickup points back to that slot, and player ownership matches when the slot is owned. It then invokes the native GetConfirmationOnInteractable on the identified target. The game's forwarding/interaction path is expected to undock if allowed.
   - The mod does not disable grab assist. With the toggle ON, its fallback may prioritize one nearby slot over a more distant grab-assist target if direct native selection found none.
   - After confirmation, 1.9.6 records whether the held object matches the original pickup, the slot, or another object, plus whether the original pickup remains docked and whether the slot now contains the original or a different pickup. These diagnostics are not proof of server persistence.
   - If confirmation throws after invocation starts, the prefix avoids immediately issuing a second native grab that might duplicate side effects. Otherwise failures fall back to ordinary game handling. Some reflection/member names and IL2CPP behavior remain unverified.

WHAT THE USER-SUPPLIED GAME SOURCE REVEALED
------------------------------------------
These are facts about the supplied Mono reference; check Quest compatibility before relying on exact implementation details.

Interactor:
- CheckHold(PlayerInput) is subscribed to Interact and HardInteract action start events. It calls OnStartInteractionAttempt, checks local/held state, then may use grab assist or SelectBest(GetColliderOverlap(), out target), and calls GetConfirmationOnInteractable.
- OnStartInteractionAttempt primarily updates the interaction timeout when timing-out is enabled. Its name alone did not establish a generally useful target callback, and the 1.9.2 run did not log it despite hook registration.
- SelectBestFromCurrent calls GetColliderOverlap and SelectBest. SelectBest builds OverlapInteractables from interactable colliders, applies IsInteractable/channels, and asks each target to AssessInteraction. It is not guaranteed to select a non-interactable or score-rejected shop item.
- The reference collider overlap uses Physics.OverlapCapsuleNonAlloc with an internal 10-element collider array, last physics trigger position, current trigger position, scaled radius and collision mask.
- GetConfirmationOnInteractable may perform forwarding and ownership/interaction checks before calling StartInteract or waiting for confirmation. StartInteract itself also performs CheckForward and CheckInteractAllowedAndReplace before Interact.
- StartInteract arguments are (Interactable, isFromNetwork, isForced, isForcingHold). Remote/network interactions must not be treated as local user grabs.

PickupDock:
- A PickupDock is itself an Interactable and may expose HasDockedPickup, DockedPickup, QuantityStored, IsOwnedByPlayer and PlayerController.
- Its CheckForward can return the docked pickup, but also contains ownership/quantity checks and mutates state including forwarding/clientDocked. Do not call it as if it were a harmless getter.
- AssessScore can reject a local grab if RawInput.HardGrab is false. Different slots/settings may behave differently.
- A docked Pickup can be marked IsInteractable=false; the slot may be the actual selectable target.

Pickup:
- Pickup extends Interactable. IsDocked is based on Dock != null.
- Pickup.Interact calls Undock(interactor, true, 1) when Dock is non-null, then performs dock-specific grab setup. Prematurely undocking can change forwarding and the isGrabbingFromDock state.
- The original mod request used the same Undock(interactor, true, 1) pattern. The current experiment leaves this call to the native interaction path rather than calling it before forwarding.
- ForwardTo is a collection in the supplied reference, not a single linked interactable. Do not use the 1.9.3 single-target diagnostic as a correct model.
